# TikTok Controlled Verification Runbook

## Purpose

This is the operator-controlled final verification for TikTok Direct Post. It proves the real OAuth account, encrypted token lifecycle, creator privacy negotiation, media upload, provider processing, and durable promotion state without enabling public posting.

The test is intentionally **SELF_ONLY**. Do not use a production audience, public visibility, rate-limit workarounds, stealth automation, proxy rotation, or artificial engagement.

## Provider contract verified

TikTok's current Direct Post documentation requires:

1. query creator information;
2. initialize `/v2/post/publish/video/init/`;
3. upload the returned `upload_url` when using `FILE_UPLOAD`;
4. poll `/v2/post/publish/status/fetch/`.

Direct Post uses the `video.publish` scope. The separate `video.upload` scope is for draft-upload flows. The Direct Post initialization endpoint is limited to six requests per minute per user access token. Creator-info and status endpoints have separate provider limits. The implementation therefore uses a per-account BullMQ lane and does not retry Direct Post initialization on HTTP 429.

## Preconditions

### TikTok Developer Console

- Content Posting API is enabled for the exact application.
- `video.publish` is approved for the application.
- `video.upload` is only required for draft-upload flows; it is not a substitute for Direct Post authorization.
- The production redirect URI is registered exactly as used by the application.
- The controlled creator account is authorized for the application.
- The operator can inspect the TikTok developer application and creator account.
- Any TikTok audit/visibility requirements applicable to public Direct Post are understood before requesting public promotion.

### Yap Engine

Required server-side configuration:

```text
NODE_ENV=production
SWARMX_TIKTOK_API_APPROVED=1
SWARMX_TIKTOK_PUBLIC_POSTS_ENABLED=0
SWARMX_TIKTOK_CLIENT_KEY=<server secret>
SWARMX_TIKTOK_CLIENT_SECRET=<server secret>
SWARMX_TIKTOK_TOKEN_ENCRYPTION_KEY=<32-byte-base64 key>
SWARMX_TIKTOK_OAUTH_REDIRECT_URI=<registered production callback URI>
DATABASE_URL=<Neon pooled connection URL>
DATABASE_URL_UNPOOLED=<Neon direct connection URL>
```

Do not put TikTok credentials or tokens in `NEXT_PUBLIC_*` variables.

## Phase 1 — Authorize the controlled account

1. Generate an application OAuth state value using the application's normal authorization flow.
2. Open the generated TikTok authorization URL.
3. Authorize the controlled creator account with the approved scopes, including `video.publish` for Direct Post. The separate `video.upload` scope applies to draft-upload flows.
4. Complete the registered callback.
5. Confirm the resulting `tiktok_accounts` row contains:
   - the correct `user_id`;
   - TikTok `open_id`;
   - encrypted access/refresh token ciphertext;
   - access and refresh expiry timestamps;
   - granted scopes;
   - status `active`.
6. Confirm no plaintext token is present in logs, browser storage, API responses, or dashboard state.
7. The application persists the real account using the existing `tiktok_accounts` contract: `id`, `user_id`, TikTok `open_id`, encrypted access/refresh token ciphertext, expiry timestamps, scopes, and `status = active`. Do not manually insert invented `account_id` or `authorization_state` columns.

TikTok's current token documentation specifies 24-hour access-token validity and 365-day refresh-token validity. Refresh-token rotation must persist a newly returned refresh token.

## Phase 2 — Prepare a controlled artifact

Use a small, rights-cleared MP4 generated by the Yap Engine.

Recommended controlled artifact:

- 9:16;
- H.264/AAC;
- 5–15 seconds;
- original or licensed assets only;
- no sensitive personal information;
- no misleading claims;
- no copyrighted material without authorization.

Record:

```text
artifact path
SHA-256
duration
file size
generation/run ID
creative run ID
```

The artifact must pass the normal technical, creative, continuity, compliance, rights, and provenance gates before upload.

## Phase 3 — Execute controlled verification

From the repository root:

```bash
pnpm --filter @swarmx/api tiktok:verify -- \
  --account-id=<DURABLE_TIKTOK_ACCOUNT_ID> \
  --output=<PATH_TO_CONTROLLED_MP4> \
  --prompt="Controlled Yap Engine integration verification — SELF_ONLY" \
  --confirm-self-only=true
```

Expected behavior:

1. the API approval gate must be enabled;
2. the durable account must be `active`;
3. the access token is resolved server-side and refreshed when necessary;
4. creator info is queried;
5. `SELF_ONLY` must be present in the returned privacy options;
6. Direct Post is initialized with `is_aigc=true`;
7. the file is uploaded using bounded chunks and `Content-Range`;
8. status is polled;
9. only a terminal `published` result promotes the account;
10. the account status becomes `controlled_verified`.

The command must fail closed on missing approval, missing account, non-active account, missing SELF_ONLY support, failed upload, or a non-published terminal result.

## Phase 4 — Verify evidence

Capture:

- command output, excluding secrets;
- publish ID;
- account ID;
- artifact SHA-256;
- timestamp;
- TikTok creator privacy options observed during the test;
- final status from `status/fetch`;
- Neon account status after the run.

Do not capture access tokens, refresh tokens, client secrets, or encryption keys.

### Pass criteria

| Check | Required result |
|---|---|
| API approval | `SWARMX_TIKTOK_API_APPROVED=1` |
| Account state before test | `active` |
| Creator privacy | `SELF_ONLY` available |
| AIGC disclosure | `is_aigc=true` |
| Upload | all chunks accepted |
| Provider status | terminal published state |
| Account state after test | `controlled_verified` |
| Public posting flag | remains `0` |

A successful controlled verification does **not** by itself authorize public posting.

## Operator-only release gate

Do not manually mutate `public.tiktok_accounts` to force `controlled_verified`. The application callback creates the durable account as `active`; only the real verification command may promote the existing row after a terminal successful provider result. Use:

```sql
SELECT id, user_id, open_id, status, scopes, updated_at
FROM public.tiktok_accounts
WHERE status = 'controlled_verified'
ORDER BY updated_at DESC;
```

The production release condition is exactly one or more real operator-controlled accounts in `controlled_verified`; absence of that state keeps Direct Post blocked. Public posting remains separately gated by `SWARMX_TIKTOK_PUBLIC_POSTS_ENABLED=0`.

## Phase 5 — Negative-path checks

Do not run these against public content.

Verify the following fail-closed behavior in staging or deterministic tests:

- API approval disabled → no Direct Post;
- account absent → Studio/manual-review fallback;
- account not `controlled_verified` in production → Studio/manual-review fallback;
- `SELF_ONLY` unavailable during controlled verification → fail;
- expired/invalid refresh grant → reauthorization required;
- Direct Post initialization receives 429 → no brute-force retry;
- status polling reaches timeout → `pending_review`, not a fabricated success.

## Phase 6 — Public promotion

Keep:

```text
SWARMX_TIKTOK_PUBLIC_POSTS_ENABLED=0
```

until all applicable TikTok audit/visibility requirements have been satisfied.

Only after operator approval may the public-post flag be changed to `1`. The first public test should still be deliberately small and observable. Record the exact configuration, commit SHA, artifact checksum, publish ID, and provider outcome.

## Rollback

Immediately restore:

```text
SWARMX_TIKTOK_PUBLIC_POSTS_ENABLED=0
```

and, where appropriate, set the account state to `disabled` or `reauthorization_required`.

Do not delete evidence required for incident review.
